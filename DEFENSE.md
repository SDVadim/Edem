# Защита проекта «Едем»

Шпаргалка к защите: что показывать, как устроен код и почему он устроен именно так. В конце — вопросы, которые вероятнее всего зададут, с ответами.

---

## 1. Проект в одном абзаце

«Едем» — каршеринг. Пользователь находит машину на карте или в каталоге, перед поездкой фотографирует её с 4 сторон, едет и видит, как растёт сумма. Потом завершает аренду по сценарию из стори-фрейма: чек-лист → проверка зоны → фотоконтроль → подтверждение → закрытие машины → чек → пуш. Отдельно проработана ветка «нет связи с машиной» (подземный паркинг): повтор, закрытие через оператора в чате, честный чек без оплаты ожидания. Продуктовая идея взята из CJM: главная боль — «спишут деньги за чужие повреждения, и я не смогу доказать». Поэтому у каждой поездки хранится акт осмотра с фото и временем снимка, и из истории можно в один клик оспорить списание.

## 3. Архитектура

### Слои

```
┌───────────────────────── Presentation ─────────────────────────┐
│  View (SwiftUI / UIKit)  ──►  ViewModel (@Observable, @MainActor)│
└───────────────────────────────┬────────────────────────────────┘
                                │ знает только протоколы
┌───────────────────────── Domain ───────────────────────────────┐
│  Модели: Car, Trip, Receipt, InspectionPhoto, ParkingZone       │
│  Логика: TariffCalculator                                        │
│  Протоколы: CarRepository, TripRepository, VehicleCommandService,│
│             SupportService, NotificationService, SettingsStore,  │
│             RentalSession, CarsRemoteDataSource, CarsCache       │
└───────────────────────────────┬────────────────────────────────┘
                                │ реализуют
┌───────────────────────── Data ─────────────────────────────────┐
│  Network: URLSessionHTTPClient, JSONAPIClient, DTO,              │
│           FleetCarsDataSource, DummyJSON*Service                 │
│  Persistence: @Model-сущности, SwiftDataCarsCache,               │
│               SwiftDataTripRepository                            │
│  Services: RentalManager, UserDefaultsSettingsStore,             │
│            LocalNotificationService, CachedImageLoader,          │
│            ConnectionAwareVehicleService (декоратор)             │
└────────────────────────────────────────────────────────────────┘
          ▲ всё собирается в одном месте: App/AppContainer.swift
```

Правило зависимостей: стрелки идут только вниз, к протоколам. Domain не импортирует ни SwiftUI, ни UIKit, ни SwiftData — это чистый Swift, поэтому его можно тестировать без симулятора.

### Почему MVVM, а не VIPER / TCA / Clean Swift

- Для 10 экранов MVVM даёт достаточное разделение без лишнего шаблонного кода.
- SwiftUI сам по себе построен вокруг «состояние → интерфейс», и `@Observable`-ViewModel ложится на это естественно.
- Тестировать удобно: ViewModel — обычный класс, ему подсовываются моки протоколов (`EdemTests/ViewModelTests.swift`).

### Структура папок

```
Edem/
├── App/            EdemApp (точка входа), AppContainer (DI), RootView (TabView), Router
├── Domain/         Модели, тариф, зона парковки, все протоколы
├── Data/
│   ├── Network/      HTTP-клиент, DTO, свой API машин, сервисы DummyJSON
│   ├── Persistence/  SwiftData-сущности и хранилища
│   ├── Repositories/ DefaultCarRepository (сеть + кэш)
│   └── Services/     Аренда, настройки, уведомления, картинки, декоратор связи

```

## 4. Ключевые части кода

### 4.1. Точка входа и внедрение зависимостей

`App/EdemApp.swift` создаёт `AppContainer` один раз и передаёт его в `RootView`.

`App/AppContainer.swift` — **composition root**: единственное место, где написано `URLSessionHTTPClient()`, `SwiftDataTripRepository(...)`, `DummyJSONVehicleCommandService(...)` и т.д. Наружу он отдаёт фабрики: `makeMapViewModel()`, `makeFinishFlowViewModel(...)` и др. Каждая фабрика передаёт ViewModel только нужные ей протоколы.

**Почему не синглтоны (`.shared`)?** Синглтон — скрытая глобальная зависимость: по коду класса не видно, что он ходит в сеть, и в тесте его не подменить. Здесь всё приходит через `init`, поэтому зависимости видны по сигнатуре, а в тестах подставляются моки.

### 4.2. Навигация

`App/RootView.swift`:
- `TabView` с 4 вкладками: Карта, Автомобили, Поездки, Профиль;
- в каждой вкладке `NavigationStack(path: $router.path)` и свой экземпляр `Router`;
- `Router` прокидывается через `.environment(router)`, экраны берут его как `@Environment(Router.self)`.

`App/Router.swift`:
- `enum Route` — все возможные переходы: `.car(Car)`, `.pickupInspection(Car)`, `.activeRental`, `.trip(UUID)`;
- `RouteDestinations` — один `navigationDestination(for: Route.self)` на всё приложение: какой экран открыть для какого маршрута.

**Почему стек хранится в массиве `path`, а не в `NavigationLink(destination:)`?** Так навигацией можно управлять из кода:
- после осмотра `router.replace(with: [.activeRental])` — экран осмотра и карточка машины убираются из истории, кнопка «Назад» не вернёт к осмотру уже начатой поездки;
- после чека `router.popToRoot()`.

**Почему у каждой вкладки свой Router?** У каждой вкладки своя независимая история: переход на другую вкладку и обратно не сбрасывает стек.

Поток завершения аренды — модальный `fullScreenCover` со своим `NavigationStack(path: $viewModel.path)` и `enum FinishStep`. Он модальный, потому что это отдельная задача с необратимым шагом: пользователь не должен случайно уйти в другую вкладку посреди закрытия машины.

### 4.3. UIKit-экран: каталог

Файлы: `Features/Catalog/CarsCollectionViewController.swift`, `CatalogCells.swift`, `CatalogScreen.swift`.

**Compositional layout, две секции:**
- `filters` — горизонтальная лента чипов (`orthogonalScrollingBehavior = .continuous`), ширина ячейки `.estimated` — подстраивается под текст;
- `cars` — сетка: 2 колонки на iPhone, 3 при ширине > 600 pt (iPad). Высота `.estimated(250)` — ячейки сами считают высоту по Auto Layout.

**Diffable data source.** `enum Item: Hashable { case filter(CatalogFilter, isSelected: Bool); case car(Car) }`. При изменении данных собирается новый `NSDiffableDataSourceSnapshot` и применяется — UIKit сам вычисляет разницу и анимирует вставки и удаления. Не нужно вручную вызывать `insertItems` / `deleteItems` и следить за индексами — частый источник крэшей.

Почему `isSelected` — часть идентификатора чипа: при смене фильтра меняется идентичность двух чипов (старого и нового выбранного). Diffable сам пересоздаёт только эти две ячейки.

**Ячейки** регистрируются через `UICollectionView.CellRegistration` (современный API вместо `register` + строковых идентификаторов). `CarCell` — `UIStackView` с Auto Layout, поддерживает Dynamic Type (`adjustsFontForContentSizeCategory`) и VoiceOver: у всей ячейки один `accessibilityLabel`.

**Картинки:** `CachedImageLoader` (протокол `ImageLoading`) с `NSCache`. В ячейке загрузка запускается как `Task`, а в `prepareForReuse` задача отменяется. Иначе при быстрой прокрутке переиспользованная ячейка показала бы картинку от предыдущей машины.

**Связь со SwiftUI** — `CarsCollectionView: UIViewControllerRepresentable`:
- `makeUIViewController` создаёт контроллер один раз;
- `updateUIViewController` вызывается SwiftUI при каждом изменении входных данных (`cars`, `selectedFilter`). Внутри он применяет новый snapshot;
- действия идут обратно через замыкания: `onSelectFilter` → `viewModel.filter = …`, `onSelectCar` → `router.push(.car(car))`, `onRefresh` → `await viewModel.refresh()` (pull-to-refresh через `UIRefreshControl`).

Поток данных: `CatalogViewModel.filter` меняется → `visibleCars` пересчитывается → SwiftUI перерисовывает `CatalogScreen` → вызывается `updateUIViewController` → новый snapshot. UIKit-контроллер не хранит своё состояние — источник правды один, это ViewModel.

### 4.4. ViewModel и `@Observable`

Все ViewModel помечены `@MainActor @Observable final class`.

- **`@Observable` (Observation, iOS 17) вместо `ObservableObject` + `@Published`.** SwiftUI перерисовывает view, только если изменилось свойство, которое этот view реально читал в `body`. Со старым `ObservableObject` любое `@Published`-изменение перерисовывало всех подписчиков. Плюс меньше шаблонного кода.
- **`@MainActor`.** ViewModel меняют свойства, которые читает UI, а UI можно трогать только с главного потока. Компилятор сам следит, чтобы изменения шли с main actor.
- **`@ObservationIgnored`** на зависимостях (`repository`, `rental`…): это не состояние экрана, следить за ними не нужно.
- Во View ViewModel хранится как `@State private var viewModel` и создаётся в `init` через `State(initialValue:)`. Так SwiftUI создаёт её один раз и не пересоздаёт при перерисовке родителя.

### 4.5. Сеть

`Data/Network/HTTPClient.swift`:
- `protocol HTTPClient` — одна функция `send(URLRequest) async throws -> (Data, HTTPURLResponse)`. Реализация `URLSessionHTTPClient`, в тестах — `StubHTTPClient`;
- `JSONAPIClient` — `get` / `post` с кодированием и декодированием JSON, проверкой статуса 2xx и своими ошибками `NetworkError`.

`Data/Network/FleetCarsDataSource.swift` и `Data/Network/DummyJSONServices.swift` — три запроса:

| Сервис | Запрос | Смысл в приложении |
|---|---|---|
| `FleetCarsDataSource` | `GET …/raw/cars.json` (свой API на GitHub Gist) | список машин со всеми данными |
| `DummyJSONVehicleCommandService` | `POST /posts/add` | отчёт о завершении аренды; `id` из ответа — номер чека |
| `DummyJSONSupportService` | `POST /comments/add` | сообщение в поддержку |

**DTO отдельно от доменных моделей** (`FleetCarDTO` ≠ `Car`). Формат сервера может поменяться — тогда меняются только DTO и `FleetCarsDataSource`, а экраны и бизнес-логика не трогаются.

**Свой API машин** — файл `cars.json` на GitHub Gist (копия в корне проекта). По каждой машине сервер отдаёт всё: id, модель, название, марку, описание, тариф, класс, госномер, топливо, чистоту, координаты и фото. Приложение ничего не генерирует: `FleetCarsDataSource.car(from:)` только перекладывает поля ответа в `Car`. Класс машины разбирается строго: неизвестное значение — ошибка ответа, а не подмена.

Почему так: публичных API с координатами и топливом машин нет, а gist бесплатный, работает по HTTPS без ключа, и данные можно менять без пересборки приложения. Сначала машины брались из каталога DummyJSON, а координаты придумывались на устройстве; переход на свой API — одна новая реализация `CarsRemoteDataSource` и одна строка в `AppContainer`.

Всё async/await, без замыканий-колбэков: код читается сверху вниз, ошибки идут через `throws`, отмена работает через `Task`.

### 4.6. База данных — SwiftData

`Data/Persistence/Entities.swift` — три `@Model`:
- `CarEntity` — кэш машин; `sortIndex`, чтобы сохранять порядок;
- `TripEntity` — поездка; чек хранится как закодированный в JSON `Receipt`;
- `InspectionPhotoEntity` — фото осмотра с `@Attribute(.externalStorage)`: большие бинарные данные SwiftData хранит отдельными файлами, а не внутри SQLite.

Связь `TripEntity.photos` ↔ `InspectionPhotoEntity.trip` с `deleteRule: .cascade`: удалил поездку — удалились её фото.

**Сущности не выходят из слоя данных.** У каждой есть `init(domain)` и `var domain`. Репозиторий отдаёт наружу обычные структуры `Car` / `Trip`.

Почему так:
1. `@Model`-объект привязан к `ModelContext` и потоку — передавать его по приложению небезопасно.
2. Экраны не зависят от SwiftData: можно заменить хранилище на Core Data или файл, не трогая UI.
3. Структуры проще сравнивать (`Hashable`) и использовать в тестах.

`SwiftDataTripRepository`:
- выборки через `FetchDescriptor` + `#Predicate`, например текущая поездка — `statusRaw != "finished"`;
- `save` работает как upsert: есть запись — обновить, нет — вставить;
- фото только добавляются, существующие не перезаписываются: акт осмотра нельзя подменить задним числом.

**Почему SwiftData, а не Core Data:** модели описываются Swift-кодом, а не `.xcdatamodeld`; нормально работает с Observation; меньше кода. Минус — минимум iOS 17, но он и так нужен для `@Observable`.

**Offline-first** (`DefaultCarRepository`): экран сначала показывает `cachedCars()` из базы мгновенно, затем `refreshCars()` идёт в сеть и обновляет кэш. Нет сети — показываются сохранённые машины с плашкой «Нет сети — показаны сохранённые машины».

### 4.7. Текущая аренда — общее состояние

`Data/Services/RentalManager.swift` (протокол `RentalSession`) — `@Observable`-объект с `currentTrip`. Он один на приложение (создаётся в `AppContainer`), поэтому карта, каталог и карточка машины видят одну и ту же аренду. Каждое изменение сохраняется через `TripRepository`, поэтому после перезапуска приложения незавершённая аренда восстанавливается.

Статусы поездки (`TripStatus`):
- `active` — едет, деньги идут;
- `closing` — нажал «Завершить», счёт остановлен, ждём машину;
- `finished` — машина закрыта, есть чек.

Если приложение закрыли в статусе `closing`, на экране поездки появится «Завершение не подтверждено машиной» и кнопка «Продолжить завершение».

### 4.8. Сценарий завершения — самая важная часть

`Features/Finish/FinishFlowViewModel.swift` — машина состояний по кадрам стори-фрейма:

| Кадр | Что в коде |
|---|---|
| 2. Чек-лист | `checklist`, `toggle`, `isChecklistComplete` — кнопка «Далее» неактивна, пока не отмечено всё |
| 3. Зона | `ParkingZone.contains` — расстояние по формуле гаверсинусов, радиус 250 м |
| 4. Фотоконтроль | общий с осмотром `InspectionViewModel(stage: .dropoff)` |
| 5. Подтверждение | `requestFinish` → `expectedTotal` → `confirmFinish` |
| 6. Закрытие | `startClosing` → `vehicleService.lockAndFinish` в `Task` |
| 6а–6в. Ошибка | `closingState = .failed(attempt:)`, `retry()` |
| 6г. Поддержка | `openSupport()` → чат → `supportResolved()` |
| 7 / 6д. Чек | `complete(...)` → `TariffCalculator.receipt` |
| 8. Пуш | `notifications.notifyRentalFinished` |

Состояние закрытия — `enum ClosingState { idle, inProgress(startedAt), failed(attempt, message), done }`. Перечисление вместо набора булевых флагов: невозможно состояние «одновременно загружается и ошибка».

**Решения из блока «Выводы по ветке» в Figma — с привязкой к коду:**

1. **Счёт останавливается в момент нажатия «Завершить».** В `confirmFinish()`: `trip.billingStoppedAt = now()`. `TariffCalculator.receipt` считает поездку до `billingStoppedAt`, а время до `closedAt` идёт в `waitingMinutes` и `waivedWaitingCost` — эти деньги показываются зачёркнутыми и не входят в `total`. Логика: пользователь не должен платить за сбой системы, который не может исправить.
2. **Честный статус после 10 секунд.** `isSlow(at:)` сравнивает время с `promisedClosingSeconds = 10`. Экран обновляется каждую секунду через `TimelineView(.periodic)`.
3. **Предупреждение о связи заранее** — на шаге зоны, а не после ошибки.
4. **Поддержка — полноценная кнопка** «Закрыть через оператора · ~5 мин» с указанным временем ответа, а не мелкая ссылка.

**Ветка «нет связи» и декоратор.** `Data/Services/ConnectionAwareVehicleService.swift` оборачивает настоящий сервис:
- в демо-режиме (тумблер в Профиле) ждёт 4 с и бросает `VehicleCommandError.noConnection`;
- любую сетевую ошибку переводит в понятную `noConnection`, HTTP-ошибку — в `.server(statusCode:)`.

Сам `DummyJSONVehicleCommandService` при этом не менялся — это принцип открытости/закрытости.

**Почему время передаётся как `now: () -> Date`:** в тесте подставляются «часы», которые можно сдвинуть на 42 минуты и проверить чек, не дожидаясь реального времени.

### 4.9. Осмотр

`Features/Inspection/InspectionViewModel.swift` — один ViewModel для осмотра перед поездкой (`.pickup`) и фотоконтроля при сдаче (`.dropoff`). Экран тоже один — `InspectionContent`. Различается только этап и текст кнопки. Повторное использование вместо копирования.

- Каждое фото — `InspectionPhoto(side, stage, imageData, takenAt)`. Время снимка видно на плитке и в акте.
- Фото уменьшается до 1280 px и сжимается в JPEG 0.7 (`UIImage.inspectionJPEGData`) — чтобы база не раздувалась.
- Камера через `UIImagePickerController` (`CameraPicker`), а если камеры нет (симулятор) — `.photosPicker` из PhotosUI.

### 4.10. Остальные экраны

- **Карта** (`Features/Map`) — MapKit для SwiftUI (`Map`, `Annotation`), пины с ценой, карточка выбранной машины, баннер активной поездки с живым таймером.
- **Карточка машины** (`Features/CarDetail`) — галерея (`TabView` + `.page`), метрики, кнопка зависит от `availability`: доступна / это моя поездка / сначала заверши другую.
- **Поездка** (`Features/Rental`) — кадр 1: таймер, сумма, двери.
- **Чат** (`Features/Support`) — отправка через POST; ответ оператора генерируется локально через 3 с, потому что у DummyJSON нет живых операторов.
- **История** (`Features/Trips`) — `List` со свайпом на удаление; детали с чеком, двумя актами осмотра и кнопкой «Оспорить списание».
- **Профиль** (`Features/Profile`) — имя и e-mail в `UserDefaults` через протокол `SettingsStore`, статистика, демо-тумблер.

### 4.11. Дизайн-система

2. На симуляторе открыть Фото, чтобы были картинки для осмотра (в симуляторе есть стандартные).
3. В Профиле тумблер «Нет связи» **выключен**.

Ход демо:

| # | Действие | Что говорить |
|---|---|---|
| 1 | Вкладка «Карта», тап по пину | Машины пришли из сети (свой API на GitHub Gist — с координатами, топливом и номерами), сохранены в SwiftData. Показываем топливо и чистоту — это боль «не видно уровня топлива» из CJM |

| 5 | «Завершить аренду» → чек-лист → зона → фото → «Завершить» | Кадры 2–5. Красная кнопка — необратимое действие, в диалоге итоговая сумма |

## 9. Вероятные вопросы и ответы

**Почему каталог на UIKit, а не карта или чат?**
Сетка карточек с фильтрами — классический случай для `UICollectionView`: compositional layout, diffable data source и переиспользование ячеек при сотнях машин. Карта и чат на SwiftUI проще и короче.

**Как SwiftUI и UIKit обмениваются данными?**
Через `UIViewControllerRepresentable`. Вниз — входные параметры, `updateUIViewController` применяет snapshot. Вверх — замыкания `onSelectCar` / `onSelectFilter` / `onRefresh`. Состояние фильтра хранится в `CatalogViewModel`, а не в контроллере — источник правды один.

**Что будет, если пользователь быстро прокручивает каталог?**
Ячейки переиспользуются; задача загрузки картинки отменяется в `prepareForReuse`, картинки кэшируются в `NSCache`, а `byPreparingForDisplay()` декодирует изображение заранее, не на главном потоке во время прокрутки.

**Почему `@MainActor` на ViewModel? Не блокирует ли это UI?**
Нет: `await` на сетевом запросе освобождает главный поток, `URLSession` работает в фоне. На main actor выполняется только обновление свойств, которые читает UI.

**Как устроен поток данных при нажатии «Завершить»?**
`ConfirmFinishDialog` → `viewModel.confirmFinish()` → `billingStoppedAt = now`, статус `closing`, фото добавляются в поездку → `rental.update(trip)` сохраняет в SwiftData → в стек добавляется `.closing` → `Task` вызывает `vehicleService.lockAndFinish` (POST) → при успехе `complete()` считает чек, статус `finished`, сохраняет, отправляет пуш, в стек добавляется `.receipt`.

**Что если приложение закроют во время закрытия машины?**
Поездка уже сохранена в базе со статусом `closing` и временем остановки счёта. При следующем запуске `RentalManager` её загрузит, на экране поездки будет «Продолжить завершение» — поток откроется сразу на шаге закрытия (`resumeClosing: true`).

**Почему `Trip` — структура, а сущность SwiftData — класс?**
`@Model` обязан быть классом и привязан к контексту. Доменная модель — значение: её безопасно передавать между слоями и потоками, сравнивать и копировать. Репозиторий конвертирует одно в другое.

**Где утечки памяти? Как вы их избегаете?**
В `Task`, которые живут дольше экрана, используется `[weak self]`: в `FinishFlowViewModel.startClosing` и в загрузке картинок `CarCell`. Задачи отменяются при уходе (`closingTask?.cancel()`, `prepareForReuse`).

**Зачем `Router` — почему не `NavigationLink`?**
Нужна программная навигация: заменить стек после старта поездки, вернуться в корень после чека. `NavigationLink(value:)` используется там, где это обычный переход (история поездок).

**Почему SwiftData, а не Core Data / Realm?**
Нативно, без сторонних зависимостей, модели — Swift-код, работает с Observation. Минимум iOS 17 уже обязателен из-за `@Observable`.

**Почему свой JSON на GitHub Gist и DummyJSON?**
Для машин нужен API, который отдаёт координаты, топливо и номер, — у публичных API такого нет, поэтому данные лежат в своём `cars.json` на GitHub Gist: бесплатно, HTTPS, без ключа, данные меняются без пересборки приложения. DummyJSON принимает POST-запросы (завершение аренды, чат) и возвращает `id`. Переход на настоящий бэкенд — снова новая реализация протокола и одна строка в `AppContainer`.

**Как тестировать без сети?**
`StubHTTPClient` возвращает заготовленный JSON; ViewModel получают моки репозиториев и сервисов; время подставляется через `now: () -> Date`.

**Почему `SWIFT_VERSION = 5.0`, а не Swift 6?**
Строгий режим конкурентности Swift 6 требует `Sendable` везде, включая SwiftData-контексты и UIKit-делегаты. Для учебного срока выбран Swift 5: изоляция по `@MainActor` уже размечена, переход на Swift 6 — следующий шаг.

**Почему пины на карте не по реальному GPS?**
Координаты машин приходят с сервера (`latitude` / `longitude` в `cars.json`). В демо это фиксированные точки в центре Москвы; в настоящем каршеринге их присылал бы телематический блок машины. Геолокация пользователя не запрашивается — на симуляторе она указывает на Купертино, демо было бы неудобным.

**Что в коде вы бы сделали иначе / слабые места?** (Честный ответ ценят.)
- `AppContainer` передаётся в несколько view для фабрик — лучше вынести протокол `ScreenFactory`;
- карта и каталог загружают машины независимо — можно сделать общий наблюдаемый кэш;
- ответ оператора имитируется локально — в проде нужен WebSocket или пуши;
- зона завершения строится в приложении вокруг машины — в проде её отдавал бы сервер;
- фото хранятся локально — в проде их нужно загружать на сервер, иначе акт не доказательство;
- нет авторизации и регистрации (этап 1 CJM).

## 10. Что можно развить

- Регистрация через Госуслуги и трекер статуса проверки документов (этап 1 CJM).
- «Умный осмотр»: сравнение фото с базой повреждений (Vision / Core ML) и автоматический акт.
- Фикс-цена по маршруту (этап 4 CJM).
- Закрытие машины по Bluetooth как резервный канал без интернета (вывод №4 из ветки).
- Перевод на Swift 6 strict concurrency.
- UI-тесты на XCUITest для сценария завершения.
